# Dialogs

`ReadDialog` returns the permission or approval dialog on screen, or nil. It is nil whenever `ReadInput` reads the input line: both harnesses hide their input box while they ask, so dialog-shaped text above a visible box is output (a fixture, a quoted screen), and Enter there would go into the input line. Code: `internal/harness/dialog.go`. A `Dialog` has the question, the body (the request, such as the command), the numbered options, the selected option, and a fingerprint: 8 hex characters of SHA-256 over the question, body and option texts with all whitespace removed. Moving the selection or a different line wrap (a re-tiled pane; tmux captures without `-J`, so a wrap can split a word) keeps the fingerprint. Until 2026-11-17 spacing was squashed to one space instead, so a wrap inside a word changed the print and every `task new` re-tile could re-announce a dialog. The cost: two requests that differ only in where their spaces are share a print.

The reader looks for the harness's footer among the last 6 non-blank lines, the rule above the request, the numbered options read top-down from the lowest `1.` line under that rule with a question ending in `?` right above it, down to the footer (numbered from 1, one of them with the selection mark `>`, `❯` or `›`; a line right under an option continues it, but not after a blank line, and on Claude Code only when indented under the option's text, since agy wraps to column 0), that question, and the body up to the `─` rule above it, however many lines that is. That rule is an unindented line of `─` as wide as the widest such line on screen (the pane on Claude Code, the dialog on agy, whose past messages sit under shorter rules); any other run of `─` is body text. Until 2026-11-18 any line of 10 or more `─`, indented or not, ended the body, so a request line such as a heredoc delimiter `<<'──────────'` hid everything above it from the body and the fingerprint, and `--expect` of a harmless request answered a `curl | sh` one (review A1). Test: `TestRuleInsideTheRequestIsBodyText`. A dialog draws one such rule. agy wraps a long command to column 0, so a command whose wrapped piece is exactly a full-width run of `─` draws a second, and which is the dialog's cannot be told: a dialog with more than one such rule above its footer is `ambiguous` (below), read from the topmost. Until 2026-11-18 the lowest one was taken for the rule, so the `curl | sh` above a wrapped run was left out of the body and the fingerprint, and the same run wrapped out of an option hid the real choices under forged ones (round-5 review D1). Test: `TestFullWidthRuleInTheRequestMakesAnAmbiguousDialog`. The cost: where a past message's rule is as wide as the dialog's (an agy pane no wider than its 60-column message rules; not seen on a real screen), a dialog with a past message on screen is ambiguous too. When the dialog's own rule is off screen (a request taller than the pane), a forged rule would be the only one on screen: see the scrollback read below for why no real harness draws one there. On Claude Code the question may wrap: lines above the `?` line belong to it up to a blank line or a rule, which Claude Code always draws between the request and the question. Dashed `╌` rules, `Tip:` lines and Claude's `│` command mark are left out of the body. A request whose rule is not on screen is read as far as the screen goes and marked `truncated`: its start is unread, so its fingerprint does not cover it, and `answer` refuses it (exit 6); `deny` still works. On a backend whose history read does not disturb the program (`term.SafeHistory`, asked per pane: tmux's `capture-pane -S`, iTerm2's `GetBufferRequest` with `trailing_lines` and `rex capture` read the terminal's own copy of the scrollback, and hc's `read --lines` only while the program reports working, blocked or error; see below) and a harness that keeps its dialog there (`Profile.ReadScrollbackDialog`: Claude Code only), the watcher, `task wait`, `answer` and `deny` read such a request again with 2000 lines of scrollback, and take that read when it ends with what the screen showed (the same question, choices and end of the request); the request is then whole, its fingerprint covers it, and it can be answered (round-6 review R2; test: `TestTallRequestIsReadFromSafeHistory`). The same holds on iTerm2, Rex and hc, measured on 2026-11-18 with Claude Code 2.1.327 asked for the same 82-line heredoc in a scratch iTerm2 3.7.6 tab (145x80) and on a private Rex 0.1.0-preview.19 server (80x24), and for a 200-line one on a private hc 0.1.19 core (200x120): each history read held the whole dialog drawn as on tmux, ended with the screen read, and was identical over repeated reads while the screen did not change (captures `claude-tall-request-{iterm2,rex,hc}-*.txt`, `claude-second-tall-request-{iterm2,rex}-history.txt`; test: `TestClaudeTallRequestFromITerm2RexAndHcHistory`, which also checks that a history cut above the dialog's rule, as a short scrollback limit leaves it, or one ending with another dialog keeps the screen's truncated read). Whether a read disturbs the program was checked with a probe in raw mode that logs every byte of its input: iTerm2 answers a history read with the same handler as a screen read, from its own copy of the buffer (`PTYSession handleGetBufferRequest`: no input, no view scroll), and the probe saw nothing, on the main screen and on the alternate screen with mouse reporting on; the same for `rex capture`. iTerm2 keeps the profile's Scrollback Lines (5000 in the default profile here); when a limit drops the dialog's rule, the history read is truncated and the request stays refused. hc reads a main-screen program's history from its own copy (`"how": "history"`, the probe saw nothing), but reads a full-screen app with mouse reporting by sending it mouse-wheel events and stitching the screens (`"how": "stitched"`, the events in the probe's log), except while the program reports working, blocked or error (`"why": "blocked"`, nothing sent). Claude Code 2.1.327 ships an alternate-screen renderer (`/tui fullscreen`), so a Claude Code pane cannot be taken for a main-screen program: hc's `HistoryIsSafe` asks `hc get` first and allows the read only in those three states. Claude Code reports `blocked` (kind `permission`) during its dialog on hc, so its tall requests are read there. A program that leaves those states in the milliseconds between `hc get` and `hc read` can still be scrolled (not closed: hc has no read that refuses to scroll; an observing `terminal.attach` never types but gives a raw stream, not text). Until 2026-11-18 iTerm2 read the screen only, the docs said Rex did too (its `rex capture` always printed the scrollback), and hc never read history for a dialog, so a tall request was refused on all three. The tmux evidence, on real harnesses in 120x40 tmux panes on 2026-11-18 (captures in `internal/harness/testdata/`, test: `TestClaudeTallRequestOnTmux`, `TestAgyTallRequestFitsThePane`): Claude Code 2.1.326 asked to run an 82-line heredoc showed its last 30 lines on screen, and tmux's scrollback held the whole dialog: one full-width rule, the ` Bash command` title, then every line indented (the command marked with `│`) but the `╌` separators. The top of an earlier tall dialog stays in the scrollback after it is answered, so in the scrollback the dialog's rule is the lowest one, and the read is `ambiguous` unless the lines under that rule are drawn that way: a full-width rule at column 0 inside the request would otherwise read as the rule, and Claude Code draws no worker text at column 0. Claude Code also withholds a one-line command too long to show (`value cannot be shown in full — approval withheld; one-time options only`). Antigravity CLI 1.5.10 draws on the alternate screen (no scrollback) and never draws a request taller than the pane: it shows 3 lines of a long command and `⋯ (78 lines hidden)`, or cuts a long line after 12 rows (5 rows in a 20-row pane) with `...`, so its rule stays on screen and the two-rule guard above applies. The hidden part of an agy request is not read, so neither the body nor the fingerprint covers it, and `--expect` cannot tell two requests apart that differ only there. Such a dialog is marked `hidden` (`Dialog.Hidden`, `"hidden": true` in `--json`): a request line that starts with `⋯` or ends with `...` or `…` (`dialogSpec.hidden`, agy only; a command that merely ends in `...` is refused too, since a refusal costs a workaround and a missed marker an approval of unread text). `answer` refuses it (exit 6) for every choice, `--persist` too, and presses no key; `deny` (Esc) works. The notice and the `task wait` block say the request is partly hidden, suggest no answer command, and name the workaround: deny, have the worker write the command to a file and run that file (`bash <file>`), read the file while that short dialog waits, then answer it. Until 2026-11-18 a lead could approve such a dialog with `--expect` and so a command it never saw. Tests: `TestPartlyHiddenAgyRequestIsNeverApproved`, `TestAgyTallRequestFitsThePane`; on real agy: `TestDialogsRealHiddenAgy` (opt-in, `TERMCTL_DIALOGS_ONLY=tmux-agy-hidden`). ctrl+g, which agy's footer offers as "edit/expand command", is not used to read the rest; checked on agy 1.5.10 in 120x40 and 120x20 tmux panes on 2026-11-18 (captures `agy-tall-request-expanded*.txt`, `agy-long-line-expanded.txt`, `agy-tall-request-allow-pattern-confirmed.txt`, `agy-ctrl-g-on-input-line.txt`; test `TestAgyExpandedRequestIsNoDialog`). On a dialog it opens an "Expanded Tool Permission Editor": a Full Command view of 21 lines (5 in a 20-row pane) with a `(1–21 of 84 lines)` counter, which scrolls 3 lines per PageDown, so an 84-line command takes 21 to 27 keys and as many reads; it word-wraps a long line, but clips a word wider than the pane (a path showed as `.../agy/o`, `ut.txt` lost), so even the expanded read is not whole. Below it an editable "Requested Permission" field holds the allow pattern of choices 2 and 3; Enter there does not run the command but confirms the pattern and rewrites those choices (a new fingerprint); Esc returns to the same dialog and drops edits. The view is stable across reads and stays open through a resize. ctrl+g that misses the dialog (it closed between the read and the key) lands on the input line, where it opens `$EDITOR` (nvim) in the worker's pane. So reading the whole request would put dozens of keys into the worker on every notice, from the watcher, which sends none today, and still miss clipped words. agy also keeps the model's tool call, with the full `CommandLine`, in `~/.gemini/antigravity-cli/brain/<conversation>/.system_generated/logs/transcript.jsonl`, and the agy process holds `conversations/<conversation>.db` open, so a pane maps to its conversation through its process's open files (`lsof`, a process per read). It is not used: which of several pending calls is on screen cannot be told when their shown lines are the same, which is the case that matters, and the file is an undocumented format of a CLI that updates itself. Before 2026-11-17 the body was cut at 20 lines above the question, so two requests that differed above that shared a print.

A dialog is `ambiguous` when a line shaped like an option (`N. text`, with or without a mark) comes out of sequence after option 1, when the one selection mark between the rule and the footer is not on an option, when more than one shows there, or when a second full-width rule shows (above). The worker's own text (a command, a path in an option) can wrap onto lines of its own shaped like a question and options, and agy wraps them to column 0, so the real options cannot be told from fake ones. An ambiguous dialog has no question or options; its body is every non-blank line from the rule to the footer, and its fingerprint covers that. The notice and the `task wait` block say it is ambiguous and suggest only `deny`, `--json` carries `"ambiguous": true`, and `answer` refuses it (exit 6). Until 2026-11-18 the reader took the lowest `1.` line above the footer as option 1 and counted marks only below it, so the review (A2) made fake `> 1. No, cancel` lines read as the options while the real "Yes" was selected. A numbered list in the request, above the question, is body text: the options are the lowest `1.` under a question, and the one mark must be on them, so forged options below the real ones carry a second mark or leave the mark off them. From that fix until the round-5 fix (both 2026-11-18) the options were read from the first `1.` under the rule, so a request holding a numbered list starting at 1 (a commit message) was ambiguous and could not be answered (round-5 review D2). Tests: `TestWrappedFakeOptionsMakeAnAmbiguousDialog`, `TestNumberedListInTheRequestIsBodyText`.

`Persist` marks every option that is not known to grant only this one request. The known one-shot texts are the whole option `Yes`, `Yes, run command`, `Yes, proceed`, `Yes, allow access` (and `allow once` forms), and any option starting with `No`, `cancel`, `deny`, `reject` or `exit`. Everything else needs `--persist` on `answer`: agy's "always allow in this conversation" and "(Persist to settings.json)", Claude's "don't ask again", "switch to auto mode" and "allow all edits during this session", and any wording a harness adds later, such as the plan dialog's "auto-accept edits". Until 2026-11-17 the guard was a keyword list of widening words, and a review found that "Yes, and auto-accept edits" passed it as one-shot; an unknown text now fails safe.

agy draws its `↑/↓ Navigate` footer under every numbered picker, a model choice too. So an agy screen is a known permission dialog only when the question asks for permission (`Run this command?`, `Allow ...?`, or a question naming permission or access) or the body says `Requesting permission`. Any other agy screen with the dialog's shape is read as an `unrecognized` dialog, not dropped: a worker stalled on it must not go unheard. In it every option but one starting with `No` or `cancel` is `[persist]`, so no picker choice is ever a one-shot answer; `deny` presses Esc. The notice and the `task wait` block say it is not a known permission dialog, and `--json` carries `"unrecognized": true`. From the first agy gate until this change (both 2026-11-17) such a screen was ignored silently: no notice, and `task wait` did not return. Tests: `TestAgyPickerIsAnUnrecognizedDialog`, `TestUnrecognizedAgyDialogIsLoud`. The real agy captures (`Run this command?`, `Allow access to this file?`) read as before, with the same fingerprints.

`Ops.Answer` reads the dialog again right before the first arrow key, presses up or down from the selected option to the chosen one, waits until the screen shows that option selected and the same fingerprint, reads it once more, and only then presses Enter. A deny reads it once and presses Esc, never Enter (see [deny](/architecture/tasks.md#answer-and-deny)). The last read happens on every path, also when the chosen option was already selected: before 2026-11-17 that path pressed Enter on whatever dialog had replaced the one read. If the dialog changed or the selection did not arrive, it stops without Enter (exit 1). A window of milliseconds between the last read and Enter remains. Digit keys are not used: they submit before anything can be checked, and hc cannot type without submitting. After Enter it waits up to 3 s for the dialog to go; still there means exit 1.

Claude shows `✽ Gesticulating… (6s · ↓ 243 tokens)`, and the wording changes; `esc to interrupt` did not appear. The match is a word, `…`, then `(`. omp shows `Working…` or a braille spinner.

# Submit

A TUI can drop an Enter that arrives while long text is still being taken in. `Submit` checks that the text left the input line, presses Enter up to three more times, and then fails with exit 4. When it cannot read the input line afterwards, it warns that the submit is not confirmed; it does not count that as success.

`msg` looks once before it types: when the harness is working (terminal status or a busy pattern), it prints `queued for ...` instead of `sent to ...`. A busy harness may hold the message until its turn ends.

# Interrupt

`Interrupt` sends the profile's keys (Esc on claude, omp and agy), then reads the input line for up to 2 s. Claude Code and agy put queued messages back on the input line when a turn is stopped, unsent. New text there fails with exit 4 and shows the start and end of the text, so a caller does not take the text on screen for a turn in progress. A draft that was there before the interrupt only warns. An unreadable input line warns.

Checked on agy 2026-11-14: a message queued during a long reply came back on the input line within 0.5 s of Esc. Found when an agent interrupted agy to make it read a queued brief sooner, saw the brief on screen, and reported agy as working.

# Idle rule

`WaitIdle` returns when all hold: the terminal's own status is not `working`, no busy pattern is on screen, the input line is visible (where `PromptRequired`), and `StableView` has not changed for `StableSeconds`.

A calibrated harness whose input line cannot be read is refused (exit 4). Sending blind could join a draft, and crashing beats corrupting. An uncalibrated harness warns and proceeds, because its parser is unproven.

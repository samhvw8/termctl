# Dialogs

`ReadDialog` returns the permission or approval dialog on screen, or nil. It is nil whenever `ReadInput` reads the input line: both harnesses hide their input box while they ask, so dialog-shaped text above a visible box is output (a fixture, a quoted screen), and Enter there would go into the input line. Code: `internal/harness/dialog.go`. A `Dialog` has the question, the body (the request, such as the command), the numbered options, the selected option, and a fingerprint: 8 hex characters of SHA-256 over the question, body and option texts with all whitespace removed. Moving the selection or a different line wrap (a re-tiled pane; tmux captures without `-J`, so a wrap can split a word) keeps the fingerprint. Until 2026-11-17 spacing was squashed to one space instead, so a wrap inside a word changed the print and every `task new` re-tile could re-announce a dialog. The cost: two requests that differ only in where their spaces are share a print.

The reader looks for the harness's footer among the last 6 non-blank lines, the rule above the request, the numbered options read top-down from the lowest `1.` line under that rule with a question ending in `?` right above it, down to the footer (numbered from 1, one of them with the selection mark `>`, `❯` or `›`; a line right under an option continues it, but not after a blank line, and on Claude Code only when indented under the option's text, since agy wraps to column 0), that question, and the body up to the `─` rule above it, however many lines that is. That rule is an unindented line of `─` as wide as the widest such line on screen (the pane on Claude Code, the dialog on agy, whose past messages sit under shorter rules); any other run of `─` is body text. Until 2026-11-18 any line of 10 or more `─`, indented or not, ended the body, so a request line such as a heredoc delimiter `<<'──────────'` hid everything above it from the body and the fingerprint, and `--expect` of a harmless request answered a `curl | sh` one (review A1). Test: `TestRuleInsideTheRequestIsBodyText`. A dialog draws one such rule. agy wraps a long command to column 0, so a command whose wrapped piece is exactly a full-width run of `─` draws a second, and which is the dialog's cannot be told: a dialog with more than one such rule above its footer is `ambiguous` (below), read from the topmost. Until 2026-11-18 the lowest one was taken for the rule, so the `curl | sh` above a wrapped run was left out of the body and the fingerprint, and the same run wrapped out of an option hid the real choices under forged ones (round-5 review D1). Test: `TestFullWidthRuleInTheRequestMakesAnAmbiguousDialog`. The cost: where a past message's rule is as wide as the dialog's (an agy pane no wider than its 60-column message rules; not seen on a real screen), a dialog with a past message on screen is ambiguous too. When the dialog's own rule is off screen (a request taller than the pane), a forged rule would be the only one on screen: see the scrollback read below for why no real harness draws one there. On Claude Code the question may wrap: lines above the `?` line belong to it up to a blank line or a rule, which Claude Code always draws between the request and the question. Dashed `╌` rules, `Tip:` lines and Claude's `│` command mark are left out of the body. A request whose rule is not on screen is read as far as the screen goes and marked `truncated`: its start is unread, so its fingerprint does not cover it, and `task answer` refuses it (exit 6); `task deny` still works. On a backend whose history read does not disturb the program (`term.SafeHistory`: only tmux, whose `capture-pane -S` reads its buffer) and a harness that keeps its dialog there (`Profile.ReadScrollbackDialog`: Claude Code only), the watcher, `task wait`, `task answer` and `task deny` read such a request again with 2000 lines of scrollback, and take that read when it ends with what the screen showed (the same question, choices and end of the request); the request is then whole, its fingerprint covers it, and it can be answered (round-6 review R2; test: `TestTallRequestIsReadFromSafeHistory`). hc's history read can scroll a full-screen app, and iTerm2 and Rex read the screen only, so there a tall request stays truncated. The evidence, on real harnesses in 120x40 tmux panes on 2026-11-18 (captures in `internal/harness/testdata/`, test: `TestClaudeTallRequestOnTmux`, `TestAgyTallRequestFitsThePane`): Claude Code 2.1.326 asked to run an 82-line heredoc showed its last 30 lines on screen, and tmux's scrollback held the whole dialog: one full-width rule, the ` Bash command` title, then every line indented (the command marked with `│`) but the `╌` separators. The top of an earlier tall dialog stays in the scrollback after it is answered, so in the scrollback the dialog's rule is the lowest one, and the read is `ambiguous` unless the lines under that rule are drawn that way: a full-width rule at column 0 inside the request would otherwise read as the rule, and Claude Code draws no worker text at column 0. Claude Code also withholds a one-line command too long to show (`value cannot be shown in full — approval withheld; one-time options only`). Antigravity CLI 1.5.10 draws on the alternate screen (no scrollback) and never draws a request taller than the pane: it shows 3 lines of a long command and `⋯ (78 lines hidden)`, or cuts a long line after 12 rows (5 rows in a 20-row pane) with `...`, so its rule stays on screen and the two-rule guard above applies. A gap remains there: the hidden part of an agy request is not read, so neither the body nor the fingerprint covers it, and `--expect` cannot tell two requests apart that differ only there (not fixed; ctrl+g in agy expands the command). Before 2026-11-17 the body was cut at 20 lines above the question, so two requests that differed above that shared a print.

A dialog is `ambiguous` when a line shaped like an option (`N. text`, with or without a mark) comes out of sequence after option 1, when the one selection mark between the rule and the footer is not on an option, when more than one shows there, or when a second full-width rule shows (above). The worker's own text (a command, a path in an option) can wrap onto lines of its own shaped like a question and options, and agy wraps them to column 0, so the real options cannot be told from fake ones. An ambiguous dialog has no question or options; its body is every non-blank line from the rule to the footer, and its fingerprint covers that. The notice and the `task wait` block say it is ambiguous and suggest only `task deny`, `--json` carries `"ambiguous": true`, and `task answer` refuses it (exit 6). Until 2026-11-18 the reader took the lowest `1.` line above the footer as option 1 and counted marks only below it, so the review (A2) made fake `> 1. No, cancel` lines read as the options while the real "Yes" was selected. A numbered list in the request, above the question, is body text: the options are the lowest `1.` under a question, and the one mark must be on them, so forged options below the real ones carry a second mark or leave the mark off them. From that fix until the round-5 fix (both 2026-11-18) the options were read from the first `1.` under the rule, so a request holding a numbered list starting at 1 (a commit message) was ambiguous and could not be answered (round-5 review D2). Tests: `TestWrappedFakeOptionsMakeAnAmbiguousDialog`, `TestNumberedListInTheRequestIsBodyText`.

`Persist` marks every option that is not known to grant only this one request. The known one-shot texts are the whole option `Yes`, `Yes, run command`, `Yes, proceed`, `Yes, allow access` (and `allow once` forms), and any option starting with `No`, `cancel`, `deny`, `reject` or `exit`. Everything else needs `--persist` on `task answer`: agy's "always allow in this conversation" and "(Persist to settings.json)", Claude's "don't ask again", "switch to auto mode" and "allow all edits during this session", and any wording a harness adds later, such as the plan dialog's "auto-accept edits". Until 2026-11-17 the guard was a keyword list of widening words, and a review found that "Yes, and auto-accept edits" passed it as one-shot; an unknown text now fails safe.

agy draws its `↑/↓ Navigate` footer under every numbered picker, a model choice too. So an agy screen is a known permission dialog only when the question asks for permission (`Run this command?`, `Allow ...?`, or a question naming permission or access) or the body says `Requesting permission`. Any other agy screen with the dialog's shape is read as an `unrecognized` dialog, not dropped: a worker stalled on it must not go unheard. In it every option but one starting with `No` or `cancel` is `[persist]`, so no picker choice is ever a one-shot answer; `task deny` presses Esc. The notice and the `task wait` block say it is not a known permission dialog, and `--json` carries `"unrecognized": true`. From the first agy gate until this change (both 2026-11-17) such a screen was ignored silently: no notice, and `task wait` did not return. Tests: `TestAgyPickerIsAnUnrecognizedDialog`, `TestUnrecognizedAgyDialogIsLoud`. The real agy captures (`Run this command?`, `Allow access to this file?`) read as before, with the same fingerprints.

`Ops.Answer` reads the dialog again right before the first arrow key, presses up or down from the selected option to the chosen one, waits until the screen shows that option selected and the same fingerprint, reads it once more, and only then presses Enter. A deny reads it once and presses Esc, never Enter (see [task deny](/architecture/tasks.md#task-answer-and-task-deny)). The last read happens on every path, also when the chosen option was already selected: before 2026-11-17 that path pressed Enter on whatever dialog had replaced the one read. If the dialog changed or the selection did not arrive, it stops without Enter (exit 1). A window of milliseconds between the last read and Enter remains. Digit keys are not used: they submit before anything can be checked, and hc cannot type without submitting. After Enter it waits up to 3 s for the dialog to go; still there means exit 1.

# Busy lines from real turns

Claude shows `✽ Gesticulating… (6s · ↓ 243 tokens)`, and the wording changes; `esc to interrupt` did not appear. The match is a word, `…`, then `(`. omp shows `Working…` or a braille spinner.

agy shows a braille spinner (`⢿  Running command...`, `⣟  Loading...`) and `esc to cancel` on the status line. While a message is queued, the status line says `Press up to edit queued messages` instead. A banner's `esc to dismiss` is not busy.

# Submit

A TUI can drop an Enter that arrives while long text is still being taken in. `Submit` checks that the text left the input line, presses Enter up to three more times, and then fails with exit 4. When it cannot read the input line afterwards, it warns that the submit is not confirmed; it does not count that as success.

`msg` looks once before it types: when the harness is working (terminal status or a busy pattern), it prints `queued for ...` instead of `sent to ...`. A busy harness may hold the message until its turn ends.

# Interrupt

`Interrupt` sends the profile's keys (Esc on claude, omp and agy), then reads the input line for up to 2 s. Claude Code and agy put queued messages back on the input line when a turn is stopped, unsent. New text there fails with exit 4 and shows the start and end of the text, so a caller does not take the text on screen for a turn in progress. A draft that was there before the interrupt only warns. An unreadable input line warns.

Checked on agy 2026-11-14: a message queued during a long reply came back on the input line within 0.5 s of Esc. Found when an agent interrupted agy to make it read a queued brief sooner, saw the brief on screen, and reported agy as working.

# Idle rule

`WaitIdle` returns when all hold: the terminal's own status is not `working`, no busy pattern is on screen, the input line is visible (where `PromptRequired`), and `StableView` has not changed for `StableSeconds`.

A calibrated harness whose input line cannot be read is refused (exit 4). Sending blind could join a draft, and crashing beats corrupting. An uncalibrated harness warns and proceeds, because its parser is unproven.
